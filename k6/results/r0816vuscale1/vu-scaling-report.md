# Duplicate User VU 확장 실험 보고서

실행일: 2026-08-16 (Asia/Seoul)

## 결론

Duplicate User 시나리오를 VU 10·50·100·200에서 9개 전략에 적용했다. 총 36개 측정, 1,080,000 iteration은 모두 완료됐지만 응답 분포와 최종 원장을 함께 통과한 것은 `JVM_LOCK`의 VU 10·50·100 세 건뿐이었다.

- 모든 DB 감사행에서 `issueCount = COUNT(DISTINCT user_id) = COUNT(DISTINCT request_id)`였고 회원별 최대 발급 수는 1건이었다. 1인 1매 제약 자체는 유지됐다.
- 비-Watch 8개 전략은 대체로 VU 10~50에서 처리량 상한에 가까웠다. VU 50→200의 RPS 증가는 0.6~8.3%에 그친 반면, VU 200 P95는 VU 10의 8.3~18.6배였다.
- 비-Watch는 VU 10·50·100에서 no-result가 0건이었지만 VU 200에서 8개 전략 합계 483건이 발생했다.
- `REDIS_WATCH`는 VU와 무관하게 약 14.8~14.9천 TIME_WAIT를 만든 뒤 `Address already in use`로 무너졌다. 각 30,000건 중 26,507~26,991건이 결과 body를 받지 못했다.
- `DIRECT`는 발급 이력과 회원 중복 제약은 지켰지만 재고 행 lost update가 재현됐다. 10,000건 발급 이력에 DB 재고 차감은 VU별 약 2.5천건뿐이었다.
- `OPTIMISTIC` VU 10은 `INTERNAL_ERROR=1,280`으로 VU 50·100보다 오히려 나빴다. 즉시 20회 재시도와 기본 Hikari pool 10의 상호작용이 원인이라는 강한 근거가 있지만, 요청별 retry 계측이 없어 추론으로 분류한다.

표시된 RPS와 전체 P90/P95/P99는 성공·중복·오류가 섞인 값이다. 특히 Watch는 빠른 연결 실패가 대부분이므로 RPS와 전체 지연을 성능 수치로 비교하면 안 된다.

### Optimistic VU 10 역전 현상

VU 10은 `SUCCESS=9,579`, `INTERNAL_ERROR=1,280`, DB 잔여 421이었다. 전송·파싱 누락은 없고 HTTP 500도 정확히 1,280건이므로 실제 retry 소진이다.

가장 유력한 메커니즘은 다음과 같다.

1. 재고 CAS 충돌 후 별도 backoff 없이 `REQUIRES_NEW` 트랜잭션을 최대 20회 즉시 반복한다.
2. Hikari 기본 최대 pool은 10개이고 VU도 10이다.
3. 대기자가 거의 없으면 같은 요청이 반환 연결을 빠르게 다시 얻어 20회 충돌을 짧은 시간에 소진할 수 있다.
4. VU 50·100에서는 pool 대기자에게 연결이 넘어가면서 비의도적인 backoff·공정성 효과가 생긴다.

실패 응답의 파생 평균 지연도 VU 10 약 284ms, VU 50 약 1,232ms, VU 100 약 2,445ms로 이 설명과 맞는다. 다만 retry 횟수 histogram과 최종 예외 원인 metric이 없으므로 확정하려면 `OPTIMISTIC`만 VU 8/10/12/20에서 반복 실행하고 retry 횟수를 계측해야 한다.

## 판정과 권장 상한

- 정확성 우선 단일 인스턴스: `JVM_LOCK`은 VU 100까지 이번 시나리오를 완전 통과했다. VU 200에서는 74건의 no-result로 전체 발급에 실패했다.
- 성능 비교 구간: 현 기본 설정에서는 VU 50이 이미 처리량 포화에 가깝고, VU 100은 tail latency와 queueing을 관찰하는 상한에 가깝다.
- 붕괴 관찰: VU 200은 알고리즘 자체보다 Tomcat/Hikari/동일 호스트의 포화 영향을 크게 측정한다.
- `REDIS_WATCH`: 현재 연결 관리 구현에서는 VU 10부터 실험 가능한 상태가 아니다. VU를 더 늘리기 전에 같은 연결에서 WATCH/MULTI/EXEC를 수행하면서 연결을 재사용하도록 구현을 수정해야 한다.

더 높은 VU의 알고리즘 확장성을 비교하려면 k6·애플리케이션·MySQL·Redis를 분리하고 Tomcat worker, Hikari pool, MySQL connection 한도를 명시적으로 고정해야 한다.

## 해석 제한

- 각 VU·전략은 한 번씩 실행했다. 실행 순서 회전과 최소 3회 반복이 없으므로 절대 성능 순위로 일반화할 수 없다.
- VU 50은 기존 역순 실행, VU 10·100·200은 별도 실행이다. JIT, DB 캐시, 온도, 백그라운드 부하가 완전히 동일하지 않다.
- `shared-iterations`는 폐쇄형 부하다. VU 증가는 고정 도착률 증가가 아니라 동시에 실행되는 worker 증가다.
- Redis 전략도 중복 확인과 발급 이력 저장에 MySQL을 사용한다. 순수 Redis 명령 벤치마크가 아니다.
- JVM Lock 결과는 단일 애플리케이션 인스턴스에만 유효하다.
- Watch의 목적지 포트를 분리해 이전 TIME_WAIT 오염은 줄였지만, 같은 Windows 호스트의 동적 포트 정책 자체는 동일하다.
- 비-Watch VU 200 no-result의 주원인을 Tomcat/Hikari 포화로 본 것은 metric/trace가 없는 추론이다.

XLSX의 `Overview`, `Scaling`, `Results`, `Environment` 시트에서 요약, 차트, 36개 감사행, 사양·병목 근거를 함께 확인할 수 있다.
