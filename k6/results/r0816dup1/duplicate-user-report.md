# Duplicate User k6 experiment report

실행일: 2026-08-16 (Asia/Seoul)

## 목적과 조건

동일한 회원이 서로 다른 `requestId`로 쿠폰을 3번 요청할 때 회원당 최대 한 건만 발급되는지, 모든 대상 회원이 한 건씩 받을 수 있는지, 최종 재고가 맞는지를 함께 확인한다.

- 쿠폰 수량: 10,000
- 대상 회원: 10,000명
- 회원당 요청: 3건
- 전략별 총 요청: 30,000건
- VU: 50
- 애플리케이션: Spring Boot 4.1.0, Java 21, 단일 인스턴스
- 격리 인프라: MySQL 8.4, Redis 7
- 부하 도구: k6 v2.2.0, `shared-iterations`
- 기대 응답: `SUCCESS=10,000`, `DUPLICATE_USER=20,000`, 나머지 결과 0

원본 데이터는 [통합 CSV](./duplicate-user-results.csv), [통합 JSON](./duplicate-user-results.json), 전략별 k6 summary JSON에 있다. `REDIS_WATCH`는 Redis TIME_WAIT가 0인 상태에서 단독 재실행한 [summary](../r0816dup2w/duplicate-user-redis-watch-19.json)를 통합 결과에 사용했다.

DB에서 `COUNT(DISTINCT user_id)`와 회원별 발급 수를 별도로 확인했다. 모든 전략에서 실제 발급된 건의 회원별 최대 수량은 1이므로 초과 중복 발급은 없었다. 다만 `OPTIMISTIC` 1명, `REDIS_DECR` 1명, `REDIS_LUA` 2명은 발급받지 못했다. `REDIS_WATCH`는 아래의 연결 자원 고갈 때문에 945명만 발급됐다.

`DIRECT`는 응답 분포와 1인 1매는 맞았지만 DB 재고에는 2,508건만 반영되어 `remaining=7,492`, `issueCount=10,000`, `consistent=false`였다. lost update가 그대로 재현됐다.

`PESSIMISTIC`과 `CONDITIONAL`은 10,000명 발급과 재고 정합성은 맞았다. 다만 어떤 중복 요청은 해당 회원의 최초 발급을 사전 조회하기 전에 통과한 뒤 재고 0을 확인해 각각 2건이 `DUPLICATE_USER` 대신 `SOLD_OUT`이 됐다.

Redis 재고 예약 전략에서는 같은 회원의 여러 요청이 재고를 일시 선점하고 DB 유니크 충돌 후 보상하는 동안 다른 회원이 품절을 받을 수 있다. 이번 실행에서 `REDIS_DECR`은 Redis 잔여 1, `REDIS_LUA`는 잔여 2로 끝났고 그만큼 대상 회원이 미발급됐다.

## REDIS_WATCH 연결 자원 고갈

기존 실행의 영향이 없는지 확인하기 위해 Redis `TIME_WAIT=0` 상태에서 `REDIS_WATCH`만 새 쿠폰으로 다시 실행했다. 동일 문제가 재현됐다.

- Windows TCP 동적 포트 범위: 16,384개
- 실행 직후 Redis 6381 포트의 `TIME_WAIT`: 14,918개
- 서버 응답을 받은 요청: 3,000건
- 전송 실패: 27,000건
- 성공: 945건
- 중복 회원: 1,778건
- 내부 오류: 277건
- Redis 잔여 재고: 9,055

WATCH 충돌 재시도에서 전용 Redis 연결이 반복 생성·종료되며 로컬 동적 포트를 소진한 것으로 판단된다. 이 상태에서는 k6 클라이언트도 8080 연결용 로컬 포트를 확보하지 못했다. Redis 기존 Java 코드는 이번 작업에서 변경하지 않고 실패 현상을 결과로 남겼다.

## 해석 제한

- 조건별 단일 실행이므로 절대 성능 순위로 일반화하면 안 된다.
- JVM Lock 결과는 단일 애플리케이션 인스턴스에서만 유효하다.
- Redis 전략도 중복 확인과 발급 이력 저장에 MySQL을 사용하므로 Redis 명령 자체의 순수 벤치마크가 아니다.
- 응답 분포 불일치와 회원당 발급 정책 실패, 재고 정합성 실패를 서로 다른 문제로 해석해야 한다.
