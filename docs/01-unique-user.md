# Unique user 시나리오

> 실행 2026-08-14 · VU 50 · 데이터 [`k6/results/r0814full2`](../k6/results/r0814full2/)

서로 다른 회원이 1회씩 요청할 때 재고보다 많이 발급되지 않는지, 재고 원장이 맞는지, 오류 응답 없이 처리되는지 확인합니다.

## 조건

| 단계 | 재고 | 전략별 요청 | 확인하는 것 |
|---|---:|---:|---|
| Basic | 100 | 200 | 기본 정합성 |
| Contention | 100 | 1,000 | 재시도·락 대기·충돌 |
| Performance | 1,000 | 10,000 | 처리량·지연 |

9개 전략 × 3단계 = 27회, 측정 요청은 모두 100,800건이고 전부 완료됐습니다. 공통 환경과 격리 방법은 [실행 환경](environment.md)에 있습니다.

## 결과 요약

- **`DIRECT`는 세 단계 모두 초과 발급했고 재고 원장이 깨졌습니다.** 재고 100에 200건, 100에 999건, 1,000에 9,997건이 발급됐습니다.
- **`JVM_LOCK`, `PESSIMISTIC`, `CONDITIONAL`, `REDIS_DECR`, `REDIS_LUA`는** 모든 단계에서 재고 수만큼 정확히 발급했고, 오류 응답 0건, 재고 원장 일치였습니다.
- **`OPTIMISTIC`, `REDIS_LOCK`, `REDIS_WATCH`는** 초과 발급이 없고 재고 원장도 맞았지만, 오류 응답이 합계 587건 나왔습니다. 정합성 실패가 아니라 가용성 저하로 분류합니다.
- 27회 중 재고 원장이 맞은 것은 24회이고, 불일치 3회는 모두 의도적인 기준선인 `DIRECT`였습니다.
- k6 응답 검증(오류 응답 0 등)은 19/27회 통과했습니다. 실패 8회는 모두 오류 응답 때문이었습니다. `DIRECT` 3회는 k6 검증은 통과했지만 원장 확인에서 실패했습니다.
- 종료 후 Redis를 교차 확인한 결과, 실험 재고 키 12개는 모두 0이었고 남은 lock 키는 없었습니다.

## Performance 단계 (재고 1,000 / 요청 10,000)

표는 전략 계열 순서입니다. 1회 실행이므로 순위로 읽지 않습니다. 지연 단위는 ms입니다.

| 전략 | 성공 | 품절 | 오류 응답 | req/s | 성공 평균 | 성공 p95 | 품절 평균 | 전체 p95 | 원장 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|:---:|
| `DIRECT` | 9,997 | 3 | 0 | 148.5 | 335.7 | 358.2 | 268.1 | 358.2 | ✗ |
| `JVM_LOCK` | 1,000 | 9,000 | 0 | 202.8 | 614.4 | 686.0 | 204.8 | 623.2 | ✓ |
| `PESSIMISTIC` | 1,000 | 9,000 | 0 | 594.0 | 423.5 | 460.4 | 46.1 | 431.1 | ✓ |
| `OPTIMISTIC` | 1,000 | 8,668 | 332 | 467.1 | 237.2 | 682.3 | 35.6 | 325.9 | ✓ |
| `CONDITIONAL` | 1,000 | 9,000 | 0 | 443.3 | 394.4 | 432.4 | 81.0 | 401.3 | ✓ |
| `REDIS_LOCK` | 1,000 | 8,815 | 185 | 391.1 | 189.1 | 239.5 | 118.0 | 211.6 | ✓ |
| `REDIS_DECR` | 1,000 | 9,000 | 0 | 1,187.0 | 106.5 | 164.8 | 34.5 | 103.2 | ✓ |
| `REDIS_LUA` | 1,000 | 9,000 | 0 | 1,335.7 | 101.4 | 126.1 | 29.9 | 101.1 | ✓ |
| `REDIS_WATCH` | 1,000 | 8,997 | 3 | 620.8 | 209.2 | 267.6 | 65.6 | 206.6 | ✓ |

요청의 90%가 품절 응답이라서, req/s는 발급 경로보다 품절 경로의 속도에 좌우됩니다.

- **`DIRECT`의 req/s가 가장 낮은 이유는 락이 아닙니다.** 요청의 99.97%가 비싼 성공 경로(재고 UPDATE + 발급 이력 INSERT)를 탔기 때문입니다. 성공 경로 평균은 335.7ms로 `PESSIMISTIC`(423.5ms)이나 `CONDITIONAL`(394.4ms)보다 짧습니다.
- **`PESSIMISTIC`의 req/s가 `CONDITIONAL`보다 높은 것은 품절 경로 차이 때문입니다** (평균 46.1ms 대 81.0ms). 성공 경로만 보면 `CONDITIONAL`이 더 빠릅니다.
- **`OPTIMISTIC`은 성공 평균(237.2ms)에 비해 성공 p95(682.3ms)가 깁니다.** 재시도를 거친 요청이 꼬리 지연을 만듭니다.

세 전략 모두 재시도나 락 획득 횟수에 상한(20회)이 있습니다. 오류 응답은 이 상한을 소진해 재고 예약 전에 끝난 요청으로 보고 있고, 최종 재고와 발급 이력은 일치했습니다. 그래서 정합성 실패가 아니라 가용성 저하로 분류합니다. 다만 요청별 실패 원인은 기록하지 않았으므로 응답 코드만으로 원인을 확정할 수는 없습니다.

## 이 시나리오의 해석 제한

- 전체 p95에는 빠른 품절 응답이 많이 섞여 있습니다. 발급 경로를 비교할 때는 성공 p95를 봅니다.
- 공통 제한은 [실행 환경 › 해석 제한](environment.md#해석-제한)에 있습니다.
